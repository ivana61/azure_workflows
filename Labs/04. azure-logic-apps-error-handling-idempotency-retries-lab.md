# Hands-on lab: Logic Apps Retry Policies

In this follow-up lab, you continue from **Lab 03: Implement task processing logic with Azure Logic Apps** and configure retry policies so transient failures are survivable.

## Audience and duration

- Audience: workshop attendees who completed Lab 03 (Logic Apps basics).
- Duration: 20-30 minutes.
- Skill level: intermediate Logic Apps designer skills.

## Learning objectives

By the end of this lab, you will be able to:

- Configure retry policies (fixed, exponential, none) on individual actions.
- Observe retry behaviour in run history (attempt count, backoff intervals).
- Distinguish transient failures (worth retrying) from permanent failures (not worth retrying).

## Prerequisites

Complete Lab 03 first. You should already have:

- An Azure subscription with an existing resource group `rg-logicapp-lab-<alias>`.
- Familiarity with the Logic Apps designer in the Azure portal.
- Azure CLI installed (optional, for resource creation via command line).

> Instructor note: This lab keeps the Logic Apps HTTP triggers with their default SAS-token authentication. In production, protect these endpoints with Azure API Management, Microsoft Entra ID, IP restrictions, or other explicit authorization patterns.

## Exercise 1: Create a Logic App with retry policies

In this exercise, you create a Logic App that calls an external HTTP endpoint with a retry policy, simulating transient failure recovery.

### Task 1: Create the Logic App resource

1. In the Azure portal, go to **Logic apps**.
2. Select **+ Add**.
3. On the **Basics** tab, configure:

   | Setting | Value |
   | --- | --- |
   | Subscription | Your lab subscription |
   | Resource group | `rg-logicapp-lab-<alias>` |
   | Logic App name | `logic-retrydemo-<alias>-<unique>` |
   | Region | Same region as the resource group |
   | Plan type | **Consumption** |

4. Select **Review + create**.
5. Select **Create**.
6. Wait for deployment to complete.
7. Select **Go to resource**.

### Task 2: Design the workflow with a retrying HTTP call

1. In the Logic App overview, select **Logic app designer**.
2. If prompted, select **Blank Logic App**.

#### Add the HTTP Request trigger

3. Search for **Request** and select **When a HTTP request is received**.
4. In **Request Body JSON Schema**, paste:

   ```json
   {
     "type": "object",
     "properties": {
       "requestId": { "type": "string" },
       "targetUrl": { "type": "string" },
       "simulateFailure": { "type": "boolean" }
     },
     "required": ["requestId", "targetUrl"]
   }
   ```

#### Add an HTTP action to call the target URL

5. Select **+ New step**.
6. Search for **HTTP** and select the **HTTP** action (built-in).
7. Configure:

   | Setting | Value |
   | --- | --- |
   | Method | `GET` |
   | URI | Click in the field, select **Dynamic content** > **targetUrl** |

#### Configure the retry policy on the HTTP action

8. On the HTTP action, select the **...** (ellipsis) menu, then **Settings**.
9. Under **Networking**, find **Retry Policy**.
10. Set the retry policy:

    | Setting | Value |
    | --- | --- |
    | Type | **Exponential Interval** |
    | Count | `3` |
    | Minimum Interval | `PT5S` (5 seconds) |
    | Maximum Interval | `PT30S` (30 seconds) |

11. Select **Done**.

#### Add a success Response action

12. Select **+ New step**.
13. Search for **Response** and select **Response**.
14. Configure:

    | Setting | Value |
    | --- | --- |
    | Status Code | `200` |
    | Headers | Key = `Content-Type`, Value = `application/json` |
    | Body | Use the expression: `json(concat('{"requestId":"', triggerBody()?['requestId'], '","status":"Success","responseBody":', body('HTTP'), '}'))` |

    Alternatively, use a simpler Body with dynamic content:

    ```
    {
      "requestId": @{triggerBody()?['requestId']},
      "status": "Success",
      "responseBody": @{body('HTTP')}
    }
    ```

15. Select **Save**.

### Task 3: Test with a working URL

```powershell
$url = "<paste-your-logic-app-trigger-url-here>"

$body = @{
    requestId = "REQ-RETRY-001"
    targetUrl = "https://httpbin.org/get"
    simulateFailure = $false
} | ConvertTo-Json

curl.exe -X POST -i $url -H "Content-Type: application/json" -d $body
```

Expected result:

- HTTP 200 response.
- Body contains the `httpbin.org` response data.
- Run history shows the HTTP action succeeded on the first attempt.

### Task 4: Test with a failing URL (observe retries)

```powershell
$body = @{
    requestId = "REQ-RETRY-002"
    targetUrl = "https://httpbin.org/status/503"
    simulateFailure = $true
} | ConvertTo-Json

curl.exe -X POST -i $url -H "Content-Type: application/json" -d $body
```

Expected result:

- The Logic App run will eventually fail (after retries are exhausted).
- In the run history, select the failed run and open the HTTP action.
- You will see the action was attempted 4 times (1 initial + 3 retries).
- The total duration reflects the exponential backoff intervals.

### Task 5: Review retry details in run history

1. Open the Logic App in the portal.
2. Select **Overview** > **Run history**.
3. Open the failed run for `REQ-RETRY-002`.
4. Select the **HTTP** action.
5. Expand the **Retry History** section â€” you will see each attempt with its timestamp, status code, and delay.

Checkpoint:

- You configured an exponential retry policy on an HTTP action.
- You observed retry behavior in run history.
- You understand how retry policies apply per action.

## (Optional) Exercise 2: Create a Logic App with scope-based error handling (try/catch)

In this exercise, you build a workflow with structured error handling using Scope actions — the Logic Apps equivalent of try/catch.

### Task 1: Create the Logic App resource

1. In the Azure portal, go to **Logic apps**.
2. Select **+ Add**.
3. Configure:

   | Setting | Value |
   | --- | --- |
   | Logic App name | `logic-errorhandling-<alias>-<unique>` |
   | Resource group | `rg-logicapp-lab-<alias>` |
   | Region | Same region |
   | Plan type | **Consumption** |

4. Select **Review + create** > **Create**.
5. Select **Go to resource** > **Logic app designer**.
6. Select **Blank Logic App**.

### Task 2: Add the HTTP Request trigger with validation

#### Add the trigger

1. Search for **Request** and select **When a HTTP request is received**.
2. In **Request Body JSON Schema**, paste:

   ```json
   {
     "type": "object",
     "properties": {
       "requestId": { "type": "string" },
       "requester": { "type": "string" },
       "item": { "type": "string" },
       "amount": { "type": "number" },
       "simulateFailure": { "type": "boolean" }
     },
     "required": ["requestId", "requester", "item", "amount"]
   }
   ```

#### Add input validation with a Condition

3. Select **+ New step**.
4. Search for **Condition** and select **Condition** (Control).
5. Configure the condition:

   - Click the left value box, select **Dynamic content** > **amount**.
   - Set the operator to **is greater than**.
   - Set the right value to `0`.

#### In the "False" branch (validation failure)

6. In the **False** branch, select **Add an action**.
7. Search for **Response** and select **Response**.
8. Configure:

   | Setting | Value |
   | --- | --- |
   | Status Code | `400` |
   | Headers | Key = `Content-Type`, Value = `application/json` |
   | Body | `{"code": "InvalidAmount", "message": "Amount must be greater than zero.", "requestId": "@{triggerBody()?['requestId']}"}` |

### Task 3: Build the Try scope (in the True branch)

#### Add a Scope for the "Try" block

9. In the **True** branch, select **Add an action**.
10. Search for **Scope** and select **Scope** (Control).
11. Rename the scope to `Try` (select the **...** menu > **Rename**).

#### Add actions inside the Try scope

12. Inside the **Try** scope, select **Add an action**.
13. Search for **HTTP** and select the **HTTP** action.
14. Configure:

    | Setting | Value |
    | --- | --- |
    | Method | `POST` |
    | URI | Use this expression: `if(triggerBody()?['simulateFailure'], 'https://httpbin.org/status/500', 'https://httpbin.org/post')` |
    | Body | `{"requestId": "@{triggerBody()?['requestId']}", "item": "@{triggerBody()?['item']}", "amount": @{triggerBody()?['amount']}}` |

15. Configure the retry policy on this HTTP action:
    - Select **...** > **Settings**.
    - Set **Retry Policy** to **Exponential Interval**, Count: `2`, Min interval: `PT5S`, Max interval: `PT15S`.
    - Select **Done**.

16. After the HTTP action (still inside the Try scope), select **Add an action**.
17. Search for **Compose** and select **Compose** (Data Operations).
18. In Inputs, enter:

    ```
    {
      "requestId": "@{triggerBody()?['requestId']}",
      "status": "Processed",
      "item": "@{triggerBody()?['item']}",
      "amount": @{triggerBody()?['amount']},
      "processedAt": "@{utcNow()}"
    }
    ```

### Task 4: Build the Catch scope

#### Add a Scope for the "Catch" block

19. After the **Try** scope (back at the True branch level, not inside Try), select **Add an action**.
20. Search for **Scope** and select **Scope**.
21. Rename it to `Catch`.

#### Configure run-after to trigger only on failure

22. On the **Catch** scope, select the **...** menu > **Configure run after**.
23. **Uncheck** "Is successful".
24. **Check** "Has failed", "Has timed out", and "Is skipped".
25. Select **Done**.

#### Add actions inside the Catch scope

26. Inside the **Catch** scope, select **Add an action**.
27. Search for **Compose** and select **Compose**.
28. In Inputs, enter:

    ```
    {
      "code": "ProcessingFailed",
      "message": "The workflow failed after retries were exhausted.",
      "requestId": "@{triggerBody()?['requestId']}",
      "failedAt": "@{utcNow()}"
    }
    ```

29. After the Compose, add another action: search for **Response** and select **Response**.
30. Configure:

    | Setting | Value |
    | --- | --- |
    | Status Code | `500` |
    | Headers | Key = `Content-Type`, Value = `application/json` |
    | Body | Select **Dynamic content** > **Outputs** from the Compose action in the Catch scope |

### Task 5: Add a success Response after the Try scope

31. After the **Try** scope (but configured to run only on success), select **Add an action**.
32. Search for **Response** and select **Response**.
33. Configure:

    | Setting | Value |
    | --- | --- |
    | Status Code | `200` |
    | Headers | Key = `Content-Type`, Value = `application/json` |
    | Body | Select **Dynamic content** > **Outputs** from the Compose action inside the Try scope |

34. On this Response action, select **...** > **Configure run after**.
35. Ensure only **"Is successful"** is checked (this should be the default).

> Important: Make sure the success Response has run-after configured on the **Try** scope (not the Catch scope). It should only execute when Try succeeds.

36. Select **Save**.

### Task 6: Test the success path

### Task 8: Test the failure path (catch scope)


## (Optional) Exercise 3: Implement idempotent request handling

In this exercise, you add patterns that prevent duplicate processing of the same request — equivalent to the deterministic instance ID and decision ID patterns in the Durable Functions lab.

### Task 1: Configure trigger concurrency and deduplication

Logic Apps Consumption triggers support concurrency control and split-on deduplication. For HTTP triggers, you can use the `x-ms-trigger-correlation-id` header or tracked properties.

1. Open `logic-errorhandling-<alias>-<unique>` in the designer.
2. Select the **When a HTTP request is received** trigger.
3. Select **...** > **Settings**.
4. Under **General**:
   - Set **Concurrency Control** to **On**.
   - Set **Degree of Parallelism** to `1`.

   This ensures that only one run processes at a time, preventing race conditions on duplicate submissions.

5. Select **Done**.
6. Select **Save**.

### Task 2: Add deduplication logic with tracked properties

To track which `requestId` values have been processed, add a tracked property:

1. On the trigger, select **...** > **Settings**.
2. Under **Tracking**, find **Tracked Properties**.
3. Add a tracked property:

   | Key | Value |
   | --- | --- |
   | `requestId` | `@{triggerBody()?['requestId']}` |

4. Select **Done**.
5. Select **Save**.

This logs the `requestId` in the run history, making it easy to identify duplicate submissions and audit processing.

### Task 3: Test duplicate request handling

Submit the same request twice:

```powershell
$url = "<paste-your-logic-app-trigger-url-here>"

$body = @{
    requestId = "REQ-IDEMP-001"
    requester = "Joni Sherman"
    item = "Key Vault change"
    amount = 750
    simulateFailure = $false
} | ConvertTo-Json

# First request
curl.exe -X POST -i $url -H "Content-Type: application/json" -d $body

# Second request (same requestId, sent immediately)
curl.exe -X POST -i $url -H "Content-Type: application/json" -d $body
```

Expected result:

- With concurrency set to 1, the second request waits until the first completes.
- Both requests succeed (Logic Apps queues the second one).
- In the run history, you can filter by the tracked property `requestId` to see both runs.

> Discussion prompt: Unlike Durable Functions where you can use the instance ID to reject a duplicate start outright, Logic Apps Consumption triggers process every valid invocation. For true deduplication, you need application-level logic (e.g., check a database for the `requestId` before processing). Standard-tier Logic Apps support stateful workflows with built-in deduplication.

### Task 4: Add application-level deduplication (optional advanced step)

For true idempotency, add a step that checks whether the `requestId` has already been processed:

1. Inside the **True** branch, before the Try scope, add a new action.
2. Search for **Azure Table Storage** (or **Azure Blob Storage**).
3. Use a **Get Entity** or **Get Blob Content** action to check if a record with the `requestId` exists.
4. Add a **Condition** that checks if the entity was found:
   - If found: return a `200` response with `"status": "AlreadyProcessed"` and an `x-idempotency-result: existing-run` header.
   - If not found: continue to the Try scope.
5. After successful processing in the Try scope, add an **Insert Entity** or **Create Blob** action to record the `requestId` as processed.

> This step is optional for the lab but demonstrates the production pattern. The concept mirrors the Durable Functions approach where the orchestration instance ID prevents duplicate workflow creation.

Checkpoint:

- You configured concurrency control on the trigger.
- You added tracked properties for observability.
- You understand the difference between platform-level queuing and application-level deduplication.

## (Optional) Exercise 4: Compare with Durable Functions error handling

Review this comparison table with the class:

| Area | Durable Functions (Lab 03 Functions) | Logic Apps (this lab) |
| --- | --- | --- |
| Retry configuration | `TaskOptions.FromRetryPolicy(...)` in code | Designer settings per action (exponential, fixed, none) |
| Try/catch pattern | `try { } catch (TaskFailedException)` in C# | Scope actions with run-after configuration |
| Error visibility | Application Insights + custom status | Built-in run history with step-by-step detail |
| Idempotent start | Deterministic orchestration instance ID; duplicate returns existing status | Trigger concurrency + application-level deduplication |
| Idempotent decisions | `decisionId` + in-memory dictionary (demo) | Check-before-process pattern with external store |
| Timeout handling | `context.CreateTimer()` + `Task.WhenAny()` | Action timeout settings + run-after on timeout |
| Side effect safety | Activities must be idempotent | Actions should use upsert patterns or unique operation IDs |
| Failure result | Orchestrator returns business failure output | Catch scope composes structured error response |
| Replay safety | Must avoid non-deterministic code in orchestrator | Not applicable (Logic Apps runtime manages state) |
| Local testing | `func start` with Azurite | Limited (VS Code extension for Standard tier only) |
| When to choose | Complex branching logic, custom code, high-performance processing | Integration-heavy workflows, low-code teams, rapid connector-based automation |

## (Optional) Exercise 5: Discuss production implementation choices

Use this checklist to guide the wrap-up discussion.

| Topic | Lab implementation | Production consideration |
| --- | --- | --- |
| Retry policy | Exponential with 2-3 attempts and short intervals | Tune attempts, intervals, and maximum duration to downstream SLA. Different actions may need different policies. |
| Error handling | Scope-based try/catch with Response actions | Add alerting (Logic Apps alerts or Azure Monitor) for Catch scope executions. Consider dead-letter queues for failed items. |
| Idempotency | Concurrency control + tracked properties | Use Azure Table Storage, Cosmos DB, or SQL to track processed request IDs. Standard-tier Logic Apps offer built-in stateful deduplication. |
| Timeout | Default action timeout | Set explicit timeouts per action. Use run-after on timeout to handle deadline breaches gracefully. |
| Error response format | Inline JSON with code and message | Standardize error schemas across all workflow APIs. Consider RFC 7807 Problem Details format. |
| Observability | Run history and tracked properties | Add Application Insights integration. Use diagnostic settings to stream logs to Log Analytics. Create dashboards for failure rates. |
| Security | Default SAS-token authentication | Add Azure API Management, IP restrictions, or managed identity authentication. Restrict which callers can invoke the workflow. |
| Side-effect safety | httpbin.org simulates external calls | Real connectors should use idempotent operations (upserts, conditional writes, unique operation IDs). |
